# WHUT 校招信息工具：架构与网页功能优化建议

## 1. 优化目标

本项目当前已经具备招聘信息采集、企业分析、宣讲会管理、简历解析、投递推荐和数据导出等完整功能。后续优化建议继续保持“本地单机、安装简单、开箱即用”的产品定位，采用模块化单体架构，不急于引入微服务或复杂的前端工程体系。

近期优化应优先解决以下问题：

1. 页面展示、企业分析和简历推荐可能使用不同的数据集合。
2. `server.py` 和 `ui.html` 承担的职责过多，继续扩展后维护成本较高。
3. 后台任务状态仅保存在内存中，服务重启后会丢失。
4. 当前以多个 JSON 文件作为主数据源，增量更新、查询和并发写入较难统一。
5. 网页功能以“查看信息”为主，尚未形成完整的求职行动和投递管理闭环。

## 2. 架构优化建议

### 2.1 建立唯一的数据主库

当前招聘数据散落在多个 `*_原始数据.json` 文件中：

- 页面展示会跨文件合并并按 ID 去重。
- 企业分析和简历推荐倾向于读取最新修改的数据文件。
- 如果最新文件只是一次“今日抓取”的小快照，分析范围可能远小于页面展示范围。

这可能造成“页面显示累计上千条招聘信息，但企业分析或推荐只使用最新几十条”的数据口径不一致。

建议使用 SQLite 作为唯一主库：

```text
data/recruit.db
├── recruitments       招聘信息
├── fairs              双选会
├── preaches           宣讲会
├── companies          企业主体
├── company_profiles   企业性质、工作地、分析版本
├── favorites          收藏记录
├── applications       投递记录
├── crawl_runs         抓取批次
├── tasks              后台任务
└── settings           非敏感设置
```

以学校网站的原始 ID 作为唯一键，通过 UPSERT 插入或更新数据。JSON、CSV 和 Markdown 改为导入、导出及备份格式，不再承担主库职责。

如果短期内不引入 SQLite，至少应建立统一的 Repository 数据访问层：

```python
repository.list_recruitments()
repository.list_companies()
repository.upsert_preaches(items)
repository.get_unanalyzed_companies()
```

抓取、分析、推荐和页面接口必须通过同一个数据访问层获取合并后的数据，不能各自选择“最新 JSON 文件”。

### 2.2 拆分 `server.py`

当前 `server.py` 同时负责：

- Flask 路由；
- 配置管理；
- 数据读取和筛选；
- 后台任务；
- 收藏管理；
- 简历推荐；
- 文件导入与导出；
- LLM 供应商管理。

建议使用 Flask Blueprint 和 Service 层拆分：

```text
app/
├── main.py
├── config.py
├── extensions.py
├── api/
│   ├── status.py
│   ├── crawl.py
│   ├── companies.py
│   ├── recruitments.py
│   ├── preaches.py
│   ├── resume.py
│   ├── tasks.py
│   └── settings.py
├── services/
│   ├── crawl_service.py
│   ├── analysis_service.py
│   ├── recommendation_service.py
│   ├── export_service.py
│   └── llm_service.py
├── repositories/
│   ├── recruitment_repository.py
│   ├── company_repository.py
│   └── task_repository.py
└── workers/
    └── task_runner.py
```

职责约定：

- `api`：校验请求参数并返回 HTTP 响应；
- `services`：实现业务规则；
- `repositories`：统一访问 SQLite 或文件；
- `workers`：运行耗时任务；
- `config`：管理配置和运行环境。

### 2.3 统一内部数据模型

当前代码直接操作学校网站返回的字典，不同模块还会将字段转换成不同的中文键名，时间、空值和线上线下类型的处理容易重复。

建议通过 `dataclass` 或 Pydantic 定义标准模型：

```python
class Preach:
    id: str
    company_name: str
    title: str
    event_type: str
    start_at: datetime | None
    end_at: datetime | None
    venue: str
    source_url: str
```

外部接口数据只在采集边界转换一次，项目内部统一使用标准字段。

建议统一的核心实体包括：

- `Recruitment`
- `Fair`
- `Preach`
- `Company`
- `CompanyProfile`
- `Application`
- `Task`

### 2.4 后台任务持久化

当前后台任务由 Flask 进程中的 `TaskManager` 管理，服务重启后任务记录和日志状态会丢失。

建议分阶段优化：

第一阶段：

- 任务状态写入 SQLite；
- 任务日志写入独立日志文件；
- Flask 重启后仍可查看历史任务；
- 使用明确的状态机：`queued`、`running`、`succeeded`、`failed`、`cancelled`。

第二阶段：

- 使用一个独立 worker 进程消费任务；
- Flask 仅负责任务创建、查询和停止；
- 避免 Web 服务重启直接中断所有任务。

本地工具无需立即引入 Celery 和 Redis，SQLite 任务表配合单 worker 即可满足需求。

任务记录建议增加：

- 总进度和当前进度；
- 当前正在处理的对象；
- 成功、失败和跳过数量；
- 错误摘要；
- 开始、结束和耗时；
- 重试次数；
- 任务参数和产物路径。

### 2.5 抽象统一的 LLM 客户端

当前已经支持多个 OpenAI 兼容供应商，但分析和推荐模块中仍存在硅基流动专用文案及部分专用变量。

建议统一封装：

```python
client = LLMClient.from_config(config)

client.chat(...)
client.vision(...)
client.list_models()
client.test_connection()
```

所有调用统一处理：

- Base URL；
- API Key；
- 模型名；
- 超时；
- 限流重试；
- JSON 解析；
- 错误格式；
- 调用日志；
- 可选的 Token 用量。

企业分析结果应保存以下元数据：

- `provider`
- `model`
- `prompt_version`
- `analyzed_at`
- `source_record_hash`
- `token_usage`
- `error`

当招聘公告变化或提示词版本升级时，可以准确识别是否需要重新分析，而不是仅按企业名称永久跳过。

### 2.6 优化配置和密钥管理

当前 API Key 明文保存在 `config.json` 中。建议：

- 普通配置继续保存在 JSON 或 SQLite；
- API Key 使用 Python `keyring` 接入 Windows 凭据管理器；
- 配置文件仅保存密钥引用；
- 设置页明确提示密钥的本地保存位置；
- 日志和错误响应统一脱敏；
- 为配置增加结构版本和迁移机制；
- 支持导入、导出不含密钥的配置模板。

### 2.7 增强采集可靠性

建议为采集器增加：

- 指数退避和随机抖动；
- 请求速率限制；
- HTTP 错误和业务接口错误分类；
- 单条详情失败时继续处理其他记录；
- 失败 ID 记录和单独重试；
- 抓取批次及耗时统计；
- 原始响应可选归档；
- 数据字段和日期异常校验；
- 开始日期不能晚于结束日期的校验；
- 学校 ID、学校代码和接口地址配置化。

### 2.8 完善日志和可观测性

建议使用 Python `logging` 替代分散的 `print`：

- 统一日志格式；
- 区分 DEBUG、INFO、WARNING、ERROR；
- 为每次抓取或分析生成 `run_id`；
- 日志自动轮转；
- API Key 等敏感内容自动脱敏；
- 页面可以按任务、等级和时间过滤日志。

### 2.9 增加自动化测试和工程化配置

建议优先覆盖：

- 跨文件合并和 ID 去重；
- 时间戳转换；
- 宣讲会日期过滤；
- 企业工作地推断；
- Markdown 报告导入；
- ICS 转义和折行；
- 推荐结果的城市及企业性质过滤；
- LLM JSON 容错解析；
- Repository 的新增、更新和查询。

建议目录：

```text
tests/
├── test_crawler_parser.py
├── test_repository.py
├── test_preach_filters.py
├── test_recommendation.py
├── test_report_import.py
└── test_ics_export.py
```

同时建议增加：

- `pyproject.toml`
- Pytest
- Ruff
- 类型检查
- 基础 CI
- 示例数据库或脱敏测试数据

## 3. 网页功能优化建议

### 3.1 首页改为“今日行动中心”

首页不应只展示静态统计，还应直接回答：

- 今天新增了哪些招聘？
- 三天内有哪些宣讲会？
- 哪些宣讲会符合目标城市？
- 哪些企业值得立即投递？
- 最近一次数据更新时间是什么？

建议首页结构：

```text
今日新增招聘  近期宣讲会  待投递企业  已收藏
      ↓             ↓           ↓
  新增列表      时间线/日历    推荐与待办
```

所有统计卡片均可点击，并跳转到已经应用对应筛选条件的页面。

### 3.2 建立统一任务中心

当前抓取、企业分析和工作地分析分别展示任务日志。建议在顶栏增加统一任务中心：

- 当前运行任务数；
- 任务进度条；
- 成功、失败和已停止状态；
- 查看详细日志；
- 停止和重试；
- 任务完成通知；
- 历史任务列表。

任务完成后自动刷新相关数据页面，并提示新增记录数量和产物位置。

### 3.3 优化招聘信息列表

建议增加：

- 单位、标题和正文综合搜索；
- 发布时间范围；
- 企业性质筛选；
- 工作城市筛选；
- 只看今日新增；
- 只看未读、已收藏或已投递；
- 按发布时间、匹配度和宣讲时间排序；
- 点击行打开详情抽屉；
- 保留筛选条件、页码和滚动位置；
- 支持多选并批量加入收藏或投递看板。

### 3.4 优化宣讲会页面

除现有表格外，建议提供：

- 列表视图；
- 周日历视图；
- 按日期分组的时间线视图。

建议增加：

- 时间冲突检测；
- “只看我能参加的”快捷筛选；
- 单场导出日历；
- 收藏时设置提前一天或两小时提醒；
- 已结束场次折叠显示；
- 公司地点和宣讲地点的来源说明；
- 从推荐结果直接收藏宣讲会；
- 同一企业多场宣讲会合并展示。

### 3.5 从“收藏”升级为“投递看板”

建议建立完整的求职进度状态：

```text
关注 → 准备投递 → 已投递 → 笔试 → 面试 → Offer → 放弃
```

每条记录可保存：

- 企业和目标岗位；
- 投递日期；
- 截止日期；
- 使用的简历版本；
- 网申链接；
- 联系人；
- 备注；
- 下次行动日期；
- 关联宣讲会。

可提供看板、表格和时间线三种视图。

### 3.6 提升推荐结果的可解释性

推荐结果建议展示：

- 总匹配分数；
- 专业匹配；
- 技能匹配；
- 地点匹配；
- 企业性质匹配；
- 匹配依据对应的简历内容；
- 当前缺失或较弱的能力；
- 推荐岗位方向；
- 数据来源和分析时间。

建议提供以下操作：

- 收藏企业；
- 加入投递看板；
- 查看企业详情；
- 查看该企业所有招聘和宣讲会；
- 标记“不感兴趣”；
- 反馈推荐是否准确。

不应只展示“高、中、低”，否则难以比较相邻推荐结果。

### 3.7 建立个人求职偏好

新增个人偏好页面，保存：

- 目标城市和优先级；
- 目标岗位；
- 专业和技能关键词；
- 企业性质偏好；
- 目标行业；
- 薪资期望；
- 是否接受出差或驻场；
- 黑名单企业；
- 不感兴趣的行业。

招聘列表、宣讲会筛选和投递推荐共用同一套偏好，避免每次重新填写。

### 3.8 增加企业详情页

建议把企业分析、招聘公告、宣讲会和投递记录关联起来：

```text
企业详情
├── 企业性质和判断依据
├── 工作地点及信息来源
├── 所有招聘公告
├── 即将举行的宣讲会
├── 推荐岗位
├── 我的收藏和投递记录
└── AI 分析时间、模型和可信度
```

企业名称应作为统一实体，处理名称别名、分公司和集团关系。

### 3.9 增加数据质量提示

页面增加数据健康状态：

- 最近抓取时间；
- 招聘主库记录数；
- 数据覆盖日期；
- 详情缺失数量；
- 未分析企业数量；
- 工作地未确定数量；
- 失败请求数量；
- 最近一次任务结果。

对于不同来源的数据使用不同标签：

- 公告明确；
- 岗位列表提取；
- AI 分析；
- 本地规则推断；
- 人工导入；
- 未确定。

避免将推断结果直接当作确定事实展示。

### 3.10 增加首次使用向导

首次启动时建议引导用户：

1. 测试学校网站连接；
2. 配置或跳过 LLM；
3. 选择抓取日期范围；
4. 执行第一次抓取；
5. 设置目标城市和岗位；
6. 查看推荐结果。

无数据页面应提供明确的下一步按钮，而不只是显示“暂无数据”。

### 3.11 改进移动端和无障碍体验

建议：

- 窄屏下将表格切换为卡片；
- 筛选区域支持折叠；
- 状态信息同时使用文字和颜色；
- 所有输入框具有明确标签；
- 支持键盘完成收藏、筛选和分页；
- 检查深色主题的文字对比度；
- 长日志采用分页或虚拟滚动；
- 为加载、成功和错误状态提供一致反馈。

## 4. 推荐实施优先级

| 优先级 | 改造内容 | 目标 |
|---|---|---|
| P0 | 统一招聘主数据口径 | 保证页面、分析和推荐使用同一份完整数据 |
| P0 | 为数据合并、推荐过滤和导出增加测试 | 防止重构引入数据错误 |
| P0 | 修复错误提示、任务失败展示和输入校验 | 提升基本可靠性 |
| P1 | 引入 Repository 和标准数据模型 | 隔离存储细节，减少重复逻辑 |
| P1 | 拆分 `server.py` | 降低维护和扩展成本 |
| P1 | 引入 SQLite 主库 | 统一增量更新、查询、收藏和投递数据 |
| P1 | 任务状态持久化 | 服务重启后仍可追踪任务 |
| P1 | 首页行动中心、任务中心和宣讲会日历 | 提升日常使用效率 |
| P2 | 统一 LLM 客户端和分析版本 | 支持多供应商和结果重分析 |
| P2 | 个人偏好、企业详情和推荐解释 | 提高推荐质量和可操作性 |
| P2 | 投递看板 | 形成完整求职管理闭环 |
| P3 | 独立 worker、通知和更多自动化 | 支持长期稳定运行 |

## 5. 分阶段实施路线

### 第一阶段：数据一致性和安全重构

1. 增加统一数据聚合模块。
2. 让页面、企业分析和简历推荐使用同一份合并数据。
3. 修复“小快照被当作完整主数据”的问题。
4. 增加核心数据处理测试。
5. 统一错误响应和日志格式。

### 第二阶段：模块化和 SQLite

1. 增加 Repository 层。
2. 建立标准数据模型。
3. 设计 SQLite 表结构和迁移脚本。
4. 将现有 JSON 数据导入 SQLite。
5. 保留 JSON、CSV、Markdown 导出能力。
6. 使用 Blueprint 和 Service 层拆分 `server.py`。

### 第三阶段：任务与 LLM 基础设施

1. 任务状态写入数据库。
2. 任务日志独立保存。
3. 建立统一任务中心。
4. 封装统一 LLM 客户端。
5. 保存模型、提示词版本和来源哈希。
6. 使用系统凭据管理器保存 API Key。

### 第四阶段：网页体验

1. 首页改为今日行动中心。
2. 招聘详情使用侧边抽屉展示。
3. 增加宣讲会日历和时间线。
4. 增加企业详情页。
5. 增加个人求职偏好。
6. 完善移动端布局和无障碍体验。

### 第五阶段：求职管理闭环

1. 增加投递看板。
2. 关联企业、岗位、宣讲会和简历版本。
3. 增加下一步行动和截止日期提醒。
4. 让推荐结果可以直接转为投递任务。
5. 根据用户反馈调整后续推荐排序。

## 7. 首要落地建议

最值得立即实施的是“统一招聘主数据口径”。

在完成该项改造前，页面列表、企业分析和简历推荐可能读取不同范围的数据。继续增加推荐算法或网页功能，会进一步放大这种不一致。

建议第一轮开发只聚焦以下交付：

1. 新增统一 Repository；
2. 跨全部招聘原始文件合并并按 ID 去重；
3. 企业分析、简历推荐和页面 API 全部改用 Repository；
4. 增加数据数量一致性测试；
5. 在总览页显示主数据数量、覆盖日期和最近更新时间。

完成后再推进 SQLite、任务持久化和投递看板，可以显著降低后续重构风险。
