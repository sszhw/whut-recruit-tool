## 三、代码层面的问题清单

按「改了能立刻见效」排序，每条都给了具体位置。

### P0 — 结构性问题（重构的主战场）

**1. `server.py` 承担 8 种职责，1455 行 / 59 路由平铺**

```
server.py 现在同时负责：
├── Flask 路由（59 个）
├── 配置读写 + API Key（load_config / save_config / get_api_key）
├── 数据读取与筛选（load_recruitments / load_preachs / _apply_preach_filters）
├── 收藏管理（load_preach_favs / save_preach_favs / fav-all / unfav-all）
├── 简历推荐编排（_recommend_preachs / api_resume_recommend）
├── 文件导入导出（api_export / api_import_report / ICS）
├── LLM 供应商管理（catalog / models / test）
└── 后台任务代理（tasks / task_log / task_stop）
```

后果：任何一处改动都要在这个巨型文件里找位置，且路由函数里混着业务逻辑，无法单独测试。

**2. `ui.html` 单文件 2036 行，40 个顶层函数**

```
ui.html 内含：
├── <style> ~800 行（三套主题：apple / light / dark）
├── <body> ~500 行（6 个 section 模板）
└── <script> ~700 行（40 个顶层函数，含 native fetch 封装、
    DOM 渲染、轮询、主题切换、收藏交互……）
```

无模块化、无构建、靠字符串拼接 HTML。三套主题的 CSS 叠加在同一处，改样式容易误伤。

**3. 轮询风暴 —— 三组长驻定时器**

```js
ui.html:1339   setInterval(pollTasks, 2000);          // 任务运行中，每 2s
ui.html:2032   setInterval(() => refreshStatus(), 15000);   // 状态
ui.html:2033   setInterval(() => loadTaskCenter(), 5000);   // 任务中心打开时
ui.html:2003   setInterval(async () => {...});              // 另一处轮询
```

空闲时也在持续请求后端，且每个请求都会触发 `repository` 的缓存查询。建议改为 SSE 单连接推送。

> **已完成**：改为 `GET /api/events`（SSE），前端 4 组定时器全部移除。
> 关键设计是**变更指纹必须便宜**——`services/status.py` 的 `status_revision()`
> 只由 `stat()` 与内存任务状态构成，完整 payload 仅在指纹变化时才构造，
> 否则每秒构造一次比原来的轮询还贵（这是 SSE 化最容易踩的反向优化）。
> 同理，前端对 `loadStats()` 与模型下拉重建也加了指纹守卫，
> 避免任务运行期间每秒重拉统计。
> 实测：静止状态下 10 秒内 `/api/status` 只请求 1 次（原先每 15 秒必有一次）。

**4. 存储层：JSON 文件仍是主库**

- 139MB 级原始文件散落在 `data/`，靠文件名带日期做版本管理
- `repository` 每次失效后要全量重解析 + 合并去重
- 多进程写依赖 `crawler.write_json()` 原子写兜底（这是上个版本修 P0 时加的补丁，不是根治）
- 收藏、任务历史、配置各写各的 JSON，没有事务边界

这是 `docs/架构与网页功能优化建议.md §2.1` 的 P1 项，也是后续投递看板的前提。

### P1 — 重复与耦合

**5. 工具函数三份**

```
plain_text:   crawler.py:51  /  resume.py:163        ← 两份实现
load_cache:   analyze.py:122 /  resume.py:153 / server.py:424   ← 三份
parse_json / truncate: 分散在 analyze.py、resume.py 各自实现
```

应统一到 `app/utils/`，或与 data model 一起收敛。

**6. `latest_*_json()` 旧习惯残留**

```python
server.py:214  def _newest_glob(pattern)          # 「取最新那个文件」
server.py:220  def latest_raw_json()
server.py:225  def latest_recruit_json()
server.py:230  def latest_preach_json()
```

这正是当初引入 `repository` 要消灭的「各读最新文件」模式。虽然注释标了"仅向前兼容"，
但只要这些函数还在，就有人会顺手用它们。**建议确认调用点后直接删除**。

**7. CLI 脚本与 Web 服务耦合了「stdout 文本协议」**

`TaskManager` 起子进程调 `analyze.py` / `resume.py` / `check_update.py`，
然后**解析子进程打印的文本**来还原进度：`parse_progress()` 从 `[3/120]`、
`已抓取详情 8/40` 这类字符串里提取数字，`error_summary()` 从输出里抓错误行。

后果：脚本改一个 print 文案，进度条就断；无法结构化；无法区分 stdout 与 stderr 语义。
建议：子进程改为输出 JSONL 事件流，父子进程之间定结构化协议。

**8. LLM 调用三处各自实现**

```
server.py  api_llm_test / _recommend_preachs
analyze.py call_api
resume.py  ocr_image_bytes / recommend
```

各自处理 base_url / key / 重试 / JSON 解析。缺统一的 `LLMClient`。

### P2 — 工程质量

**9. 没有数据模型**：全程 `dict` + 中文键名（`"单位"`、`"工作地城市"`）。
跨模块传参靠约定，改名即炸。建议用 `dataclass` 定义 `Recruitment / Fair / Preach / Company / Application`。

**10. `print` 而非 `logging`**：`run_daily.py`、`crawler.py` 大量 print，无级别、无轮转、无 run_id。
`server.py` 有一套自研的 `log_event()`，但没和 Python 标准库打通。

**11. 无鉴权**：服务绑 localhost 缓解，但 `main()` 打印了警告就放行。
如果将来加 `--host 0.0.0.0` 或做远程访问，需要先补一层 token。

**12. 缺 CI**：pyproject 配了 pytest + ruff，但没有自动化流水线，也没有类型检查（mypy/pyright）。

## 五、分阶段重构路线

原则：**每阶段独立可发布，跑通测试再进下一阶段。** 不要让重构和新功能同时进行。

### 阶段 0：安全网加固（0.5 天，先做）

在动任何结构之前，先保证改坏了能被发现。

- [x] 补 CI（GitHub Actions）：`pytest`（矩阵 3.11-3.13）+ `ruff check`
- [ ] 引入类型检查 `pyright` —— 配置已加（`pyproject.toml` 的 `[tool.pyright]`，
      basic 模式），但**尚未清完既有报错、也尚未进 CI**：openpyxl / python-docx
      不随包提供类型标注，`Workbook()` 会被推断成 Unknown 并带出一串假错，
      故先把 `reportMissingImports` 设为 warning。要真正启用需先补类型桩或加忽略。
- [x] 对现有测试做一次全绿验证，作为基线（当时 56 → 60 项）
- [x] 补一组 API 冒烟测试：`tests/test_api_smoke.py` 自动遍历 `url_map`

**验收**：CI 绿，修改任何文件都能被告知是否破坏现有行为。

### 阶段 1：去重与分层准备（1 天）

不改对外行为，只做内部清理，风险最低。

- [x] 建 `app/utils/text.py`，合并 `plain_text` / `truncate` / `extract_json_object`
- [x] `load_cache` / `save_cache` 收敛到一处（`utils/io.py`，原子写）
- [x] 删除 `server.py` 的 `_newest_glob` / `latest_*_json()`
      （改为 `repository.latest_source_file()`，仅供界面展示）
- [x] `TaskManager` 与 `server.py` 的依赖解耦：路径改为**显式参数注入**，
      不再隐式依赖模块级全局变量

**验收**：ruff 无新增告警（基线 26 → 0），测试全绿，功能零变化。

### 阶段 2：拆 `server.py` → Blueprint + Service（2-3 天）

**这是本次重构的核心动作。**

- [x] 建 `app/extensions.py`（任务管理器实例，打断循环导入）
      —— Flask app 本身仍由 `create_app()` 工厂产，不放进 extensions
- [x] 按 §4 的 `api/` 分组，把 40 个路由逐个迁到 Blueprint，**路由函数体保持原样**
      —— 第一步只做「物理搬迁」，不做「逻辑改写」，避免同时引入两类变更
- [x] 第二步：业务逻辑下沉到 `services/`（preaches / reports / recommend / exporting），
      路由只留「取参数 → 捕获 ServiceError → 拼响应」；分页等 HTTP 概念仍留在路由
- [x] 应用工厂 `create_app()` 组装（未另起 `main.py`，入口仍为 `server.py`）

**关键风险**：循环导入。解法是所有 Blueprint 在 `api/__init__.py` 统一注册，
依赖从 `extensions` / `dataloaders` 单向流入。

**已落地结构**（`server.py` 1449 → 194 行）：

    settings(终点, 零业务依赖) ← extensions/dataloaders ← services/ ← api/*.py ← server.py

职责划界：`dataloaders` 只取数，`services` 只管规则（不 import flask），
`api` 只管 HTTP 壳。业务层与 HTTP 层靠一个 `ServiceError(message, status)` 解耦——
业务层不知道状态码，路由不判断业务规则。

**第二步下沉时的两个教训**：
- 路由与服务之间靠关键字参数接线，参数名写错不会在导入时报错，
  只会在请求时抛 TypeError → 500。为此冒烟测试补了**空体 POST 遍历**
  （此前只遍历 GET，POST 完全没覆盖）；并把每个 POST 路由强制登记为
  「可安全冒烟」或「有副作用」两类之一，新增路由时漏分类会直接测试失败。
- 搬迁时顺手发现并修掉一个既有 bug：推荐降级分支在 `result` 被覆盖**之后**
  才取 `error`，提示语里填的是降级结果的错误而非 AI 的原始错误。

`settings` 只依赖 `providers` + `utils`；`DEFAULT_MODEL` 上移到 settings，
analyze / resume 反向引用（此前 settings import analyze 拿常量，会把 requests 拖进配置层，
且等 repository 日后 import settings 取 DATA 路径时会直接成环）。
`tests/test_layering.py` 固化了这三条约束。

**验收**：40 个路由路径与拆分前**逐条比对完全一致**，对外 URL 零变化；
只读接口真实启动全 200，测试 84 项全绿。

### 阶段 3：SQLite 主库（3-5 天）

- [x] 设计表结构（`app/sqlite_store.py`，原生 DDL，未引入 Alembic）
- [x] 一次性导入脚本 `scripts/migrate_to_sqlite.py`，带 JSON / SQLite 双口径校验
- [x] 存储实现落地在 `sqlite_store.py`，**`repository.py` 对外签名与返回结构零变化**
      —— 上层代码一行未改，这是当初 P0 让 repository 承担隔离职责的价值兑现
- [x] 开关切换：环境变量 `WHUT_STORE=sqlite|json`，默认 sqlite；
      库缺失 / 为空 / 损坏 / 与磁盘不同步且同步失败时自动回落 JSON，**绝不白屏**
- [ ] 收藏 / 任务历史 / 配置迁入数据库（暂缓：这三处量小，JSON 已够用）

**实测（真实 data/：2369 招聘 + 43 双选会 + 875 宣讲会）**

| 场景 | 耗时 |
|---|---|
| JSON 口径 `master_summary()` | 0.52s（每次缓存失效都要付） |
| SQLite 冷启动（含全量建库 56MB） | 0.77s（一次性） |
| SQLite 之后每次 `master_summary()` | **0.021s**（约 25×） |

两口径记录数与 ID 集合逐项一致。

**两个设计取舍，都是踩出来的**：
1. **默认目录才自动建库**。`raw_items_in()` 会被传进任意用户目录（`resume.py:155`），
   在那里落 56MB 文件违反最小惊讶原则，故只在默认数据目录冷启动建库，
   显式传入的其他目录只读不写盘。
2. **导入逻辑全项目只有一份**。`sqlite_store.import_all()` 同时被运行时冷启动与
   迁移脚本调用，避免「脚本导入」和「运行时导入」两套实现对不上。

## 六、几个建议

1. **不要让「重构」和「加功能」并行**。阶段 2、3 期间先冻结新功能，否则会在半成品结构上堆代码，比不重构更糟。

2. **如果只是想让代码更清晰，做阶段 0 + 1 + 2 就够了**（约 4 天）。
   SQLite 迁移投入大、收益偏中长期，可以在投递看板成为硬需求时再做。

3. **前端可以先不动**。`ui.html` 虽然 2036 行，但它改的是 UI 而非数据，
   风险集中在后端。建议优先做 SSE 替代轮询这一项（收益立竿见影），
   模块化拆分可以等前端复杂度真的撑不住时再说。

4. **`docs/架构与网页功能优化建议.md` 写得很扎实**，它和本文的关系是：
   那份文档回答「该有什么」，本文回答「现在在哪、怎么走到」。
